# MyMini 프로젝트 개요서

> 회의를 이끌어 줄 리더도, 정해진 진행 방식도 없는 학생·사회초년생 팀을 위한 **AI 회의 보조자**
> 1. 몇 명이 빠져서 원래는 열 수 없던 회의를, 불참자의 미니미가 대신 참석해서 **진행할 수 있게** 한다.
> 2. 내가 참석하더라도, 내 미니미와 함께 내 의견과 결론을 **2차로 검증**할 수 있다.

- 저장소: `zonxwon/mymini-backend` (작업 브랜치: `itsdongjunday`)
- 단계: 초기 MVP
- 문서 상태: 기획 방향을 새로 정리한 버전. 코드는 아직 이 방향에 맞게 수정되지 않았다. (8장 참고)

---

## 1. 한 줄 정의

팀원별 **페르소나 AI(미니미)** 가 ① 불참자를 대신해 회의가 성립하도록 돕고, ② 참석자의 의견을 함께 2차 검증하고, ③ 발언을 다듬고 회의가 안건에서 벗어나지 않게 돕는 팀 회의 보조 서비스.

## 2. 문제 정의

학생과 사회초년생 팀은 대기업처럼 연차가 쌓인 팀 리더나 정해진 회의 프로세스가 없다. 그래서 회의에서 다음 어려움을 겪는다.

| Pain point | 설명 |
|---|---|
| 리더·프로세스 부재 | 누가 진행하고, 어떤 순서로 논의하고, 어떻게 결론을 내는지 정해져 있지 않다. |
| 일정 관리 | 일정 조율이 깔끔하지 않아 팀원이 모두 모이기 어렵다. |
| 인원 부족으로 회의 불가 | 일부가 빠지면 원래는 회의를 할 수 없거나, 불참자 의견이 빠진 채 결정된다. |
| 검증 부족 | 리더나 경험자가 없어서 참석자의 의견과 결론을 한 번 더 점검해 줄 사람이 없다. |
| 흐름 이탈 | 핵심 대화에서 벗어나 다른 이야기로 흐르면서 비효율적인 회의가 되기 쉽다. |

일정 관리는 문제로 인식하지만, **이번 MVP의 기능 범위에는 포함하지 않는다.**

## 3. 대상 사용자와 시나리오

**대상**: 팀 프로젝트를 하는 학생, 첫 직장에서 팀 회의를 하는 사회초년생

### 시나리오 A. 인원이 빠져도 회의를 연다 (대리 참석)

'스피치와 토론' 수업 팀 프로젝트, 4인 팀

1. 팀원 4명이 각자 자신의 페르소나를 만들고, 조사한 보고서를 등록한다.
2. 회의 당일 2명만 참석할 수 있다. 원래라면 회의를 미뤄야 하지만, 불참하는 2명이 자신의 페르소나를 **대리 참석(ON)** 으로 켜 둔다.
3. 안건이 논의되면 불참자의 미니미가 보고서를 근거로 "그런데 저는 ~라고 생각해요"라고 적절한 타이밍에 말한다.
4. 회의가 끝나면 의견, 충돌 지점, 결론이 정리된다. 돌아온 불참자는 요약을 보고 자기 의견이 어떻게 반영됐는지 확인한다.

### 시나리오 B. 전원이 참석해도 2차 검증을 한다

1. 참석자가 의견이나 결론을 낸다.
2. 그 사람의 미니미가 본인의 보고서와 기존 발언에 비추어 **근거가 충분한지, 앞뒤가 맞는지, 놓친 점은 없는지** 점검해 알려 준다.
3. 다른 팀원도 필요하면 자기 미니미에게 같은 방식으로 검증을 요청한다.
4. 사람이 검증 결과를 보고 의견을 고치거나 그대로 간다. 결정은 항상 사람이 한다.

### 공통

- 표현이 막히면 프롬프트로 자기 미니미에게 부탁해 다듬어진 문장으로 발언한다.
- 대화가 안건에서 벗어나면 AI가 안건을 상기시키고 진행 방향을 제안한다.

## 4. 솔루션 원칙

**AI는 대화의 주체가 아니라, 적절히 개입하는 보조자다.**

- AI가 모든 대화를 나누지 않는다. 사람이 회의의 주인이다.
- 미니미는 ① 불참한 사람의 의견을 회의에 올리고, ② 참석한 사람의 의견을 검증하는 두 역할을 한다.
- 개입은 필요할 때만 한다. 빈번한 개입은 회의를 오히려 방해한다.
- 불참자의 의견을 대신 전할 때는 **근거가 있는 내용만** 말한다.
- 최종 결정은 사람이 한다. 미니미의 발언과 검증은 참고 의견이다.

## 5. 페르소나 준비 조건 (서비스의 전제)

사람별 페르소나가 의미를 가지려면 그 사람에 대한 학습 자료가 있어야 한다. 자료가 없으면 어떤 페르소나든 비슷한 말만 하게 된다. 따라서 이 서비스는 **"준비된 페르소나"를 전제로 사용한다.**

### 준비 경로

| 경로 | 시점 | 내용 |
|---|---|---|
| 보고서 등록 | 사전 | 본인이 개별적으로 조사한 보고서를 등록한다. 가장 확실한 근거 자료다. |
| 대화 누적 | 사후 | 실제 회의 대화가 쌓이면 그 사람의 발언을 페르소나에 반영한다. |

### 안전장치

- **준비도 표시**: 페르소나마다 학습 자료가 충분한지 보여 준다. 부족하면 대리 참석을 켤 때 경고한다.
- **근거 없을 때의 동작**: 보고서나 기존 발언에 없는 주제가 나오면 의견을 지어내지 않는다. 대신 "이 부분은 보고서에 없어서 ○○ 님께 확인이 필요해요"처럼 말한다.
- **근거 표시**: 대리 발언에는 어떤 자료에 기반했는지 함께 표시한다.
- **말투·성향 설정**은 보조 요소다. 페르소나의 중심은 보고서와 누적 대화다.

> 여기서 "학습"은 모델을 새로 훈련하는 것이 아니다. 페르소나 설정과 등록된 자료를 **검색해서 근거로 사용하는 방식**이다.

## 6. 핵심 기능

| # | 기능 | 설명 |
|---|---|---|
| 1 | **대리 참석** | 인원이 빠져도 회의가 성립하도록, 불참자의 미니미가 보고서를 근거로 적절한 타이밍에 의견을 말한다. |
| 2 | **2차 검증** | 참석한 사람도 자기 미니미에게 검증을 맡긴다. 미니미가 본인의 보고서와 기존 발언에 비추어 근거 부족, 모순, 놓친 점을 짚어 준다. |
| 3 | **발언 다듬기** | 표현을 정하기 어렵거나 깔끔한 진행 방식을 못 떠올릴 때, 프롬프트를 입력하면 내 페르소나가 다듬어서 말한다. 한 줄만 던져도 풀어서 올릴 수 있다. |
| 4 | **회의 흐름 유지** | 대화가 안건에서 벗어나는 것을 감지해 안건을 상기시키고 진행을 제안한다. |
| 5 | **온/오프** | 사람별 스위치. 켜면 그 사람의 미니미가 대리 참석한다. 돌아오면 끄고, 본인에게만 부재 중 요약을 보여 준다. |
| 6 | **상호작용 모드** | 대리 참석 중인 미니미가 어떻게 말할지 정한다. 아래 표 참고. |

> 2차 검증은 참석 여부와 상관없이 쓸 수 있다. 온/오프가 꺼진 사람도 호출형으로 자기 미니미에게 검증을 요청할 수 있다.

### 상호작용 모드

| 모드 | 동작 | 용도 |
|---|---|---|
| **개입형** (기본) | 흐름상 필요하다고 판단될 때만 발언 | 회의를 방해하지 않는 보조 |
| **상호작용형** | 참석자가 입력할 때마다 부재자 페르소나가 응답 | 불참자와 실시간 대화하는 느낌 |
| **호출형** | 사용자가 프롬프트로 요청할 때만 발언 | 2차 검증, 발언 다듬기, 필요할 때 의견 묻기 |

상호작용형에서 대리 참석 중인 사람이 여럿이면 기본값은 **가장 관련 있는 1명만 응답**한다. 대화가 길어지는 것과 AI 호출 비용을 줄이기 위해서다. 설정으로 "전원 응답"으로 바꿀 수 있게 한다.

## 7. 사용 흐름

**회의 전**
- 페르소나 생성, 보고서 등록, 준비도 확인
- 회의방 개설, 안건 입력

**회의 중**
- 참석자는 직접 발언하거나 미니미에게 맡기고, 필요하면 **2차 검증**을 요청한다.
- 불참자는 온/오프와 모드에 따라 미니미가 대리 참석한다.
- 대화가 안건에서 벗어나면 AI가 개입한다.
- 근거가 필요하면 검색 도구로 자료를 조사한다.

**회의 후**
- 회의 결과 자동 정리: 안건, 주요 의견, 의견 충돌, 결론
- 복귀한 사람에게 부재 중 요약 제공
- 이번 회의의 대화를 페르소나 학습 자료로 누적

## 8. 현재 구현 상태와 앞으로 필요한 것

초기 MVP 코드는 이 기획 이전에 "AI 미니미끼리 토론하는 서비스"로 작성되었다. 일부는 새 방향에 그대로 쓸 수 있고, 일부는 바꿔야 한다.

| 기능 | 현재 코드 | 새 방향과의 관계 |
|---|---|---|
| 자리 비움 → 대리 참석 | 구현됨 (`orchestrator.set_away`) | 온/오프로 확장 필요 |
| 부재 중 요약 | 구현됨 (`llm.digest`) | 그대로 사용 가능 |
| 한 줄 위임 풀어쓰기 | 구현됨 (`llm.expand`) | 발언 다듬기의 기초 |
| 회의 결과 정리 | 구현됨 (`llm.minutes`) | 그대로 사용 가능 |
| 검색 도구 | 구현됨 (`tools.py`, Tavily) | 그대로 사용 가능 |
| 오케스트레이터 | AI끼리 최대 4라운드 자동 토론 | **방향 변경 필요**: 사람의 발언에 반응하는 구조로 변경 |
| 2차 검증 | 없음 | 신규 (본인 보고서·기존 발언과 대조해 근거, 모순, 놓친 점 점검) |
| 페르소나 | 말투·성향 텍스트와 최근 발언 20개 | **보고서 등록과 검색 기반으로 확장 필요** |
| 상호작용 모드 3종 | 없음 | 신규 |
| 안건 이탈 감지 | 없음 | 신규 |
| 준비도 표시, 근거 표시 | 없음 | 신규 |
| 저장소 | 인메모리 | PostgreSQL + pgvector로 교체 예정 (보고서 검색에 필요) |

## 9. 차별점

| 비교 대상 | 한계 | MyMini |
|---|---|---|
| 일반 챗봇 | 회의 맥락 밖에서 혼자 대화하고, 팀원별 입장을 모른다. | 팀원별 페르소나와 보고서를 근거로 회의 안에서 말한다. |
| 회의록 요약 도구 | 끝난 회의를 정리할 뿐 회의 진행에는 관여하지 않는다. | 회의 중에 개입해 흐름을 유지하고, 의견을 2차 검증한다. |
| 메신저·화상회의 | 인원이 빠지면 회의를 열 수 없고, 불참자는 논의에서 완전히 빠진다. | 불참자의 미니미가 근거와 함께 의견을 내서 회의를 진행할 수 있다. |

## 10. 한계와 로드맵

**한계**
- 학습 자료가 없는 초기 사용자에게는 효과가 제한된다. 그래서 보고서 등록 또는 대화 누적을 전제로 한다.
- 대리 발언은 불참자 본인의 판단을 대체할 수 없다. 최종 결정은 본인이 확인한다.
- 개입 시점의 판단이 LLM에 의존하므로 임계값과 모드 조정이 필요하다.

**로드맵**
1. 오케스트레이터를 사람 발언 중심 구조로 바꾸고, 온/오프와 상호작용 모드 3종 구현
2. 보고서 등록과 검색 기반 근거 발언 구현 (PostgreSQL + pgvector)
3. 2차 검증, 안건 이탈 감지, 준비도 표시, 근거 표시
4. 인증과 CORS 제한 등 배포 전 보안 정비
5. Railway / Render 배포

# 부록: 기술 문서

> 아래는 **현재 코드 기준**의 기술 정보다. 새 방향 구현에 따라 바뀔 수 있다.

## A. 기술 스택

- **백엔드**: Python, FastAPI, WebSocket(uvicorn), httpx
- **LLM**: OpenAI `gpt-4o-mini` (`OPENAI_API_KEY`가 없으면 키워드 기반 MOCK 모드로 동작)
- **검색**: Tavily API (키가 없으면 모의 결과)
- **저장소**: 인메모리 (서버 재시작 시 초기화)
- **Claude API 전환**: `app/llm.py`의 `client()`와 `_json()`만 수정하면 가능하다. 다만 Claude에는 `response_format` 옵션이 없어서 JSON 출력을 프롬프트로 지시하고 파싱해야 한다.

## B. 폴더 구조

```
mymini-backend/
├─ app/
│  ├─ main.py          FastAPI 앱, REST + WebSocket 엔드포인트
│  ├─ orchestrator.py  토론 루프, 자리 비움, 회의 종료
│  ├─ llm.py           score / reply / expand / digest / minutes (키 없으면 MOCK)
│  ├─ tools.py         웹 검색 Tool (Tavily)
│  ├─ store.py         인메모리 Hub (방·소켓·메시지·기본 페르소나 3인)
│  ├─ models.py        Persona / Message / Room 데이터 클래스
│  ├─ config.py        환경변수와 상수
│  └─ static/client.html   테스트용 WebSocket 클라이언트
├─ demo-v1.html        서버 없이 동작하는 스크립트 시연 화면
├─ requirements.txt
├─ .env.example
└─ README.md
```

## C. API

| 종류 | 경로 | 설명 |
|---|---|---|
| GET | `/` | 테스트 클라이언트 |
| GET | `/health` | 동작 모드(mock/openai), 모델명 |
| GET | `/rooms/{room_id}/messages` | 메시지 목록 |
| GET | `/rooms/{room_id}/personas` | 페르소나 목록 |
| PUT | `/rooms/{room_id}/personas/{user_id}` | 페르소나 생성·수정 |
| WS | `/ws/{room_id}/{user_id}` | 실시간 회의방 |

### WebSocket 프로토콜

클라이언트 → 서버

| type | 필드 | 설명 |
|---|---|---|
| `message` | text, mode(`direct`/`delegate`) | 직접 발언 / 한 줄 위임 |
| `away` | value(bool) | 자리 비움 on/off |
| `agenda` | text | 안건 설정 (120자 제한) |
| `end_meeting` | - | 회의 결과 정리 |
| `ping` | - | 연결 확인 (`pong` 응답) |

서버 → 클라이언트: `history`, `message`(kind: human / mini / system / tool / result / digest), `presence`, `orchestrator`(scores, pick, why, threshold, round), `typing`, `agenda`, `activity`

## D. 현재 오케스트레이터 동작 (변경 예정)

1. 새 메시지가 올라오면 각 미니미의 관련도 점수(0~1)를 LLM이 계산한다.
2. 자리 비운 사람의 미니미는 `+0.3`, 참여 중인 사람의 미니미는 `×0.85`로 보정한다.
3. 방금 직접 말한 사람의 미니미와 직전에 발언한 미니미는 `0`으로 한다.
4. 임계값(`SPEAK_THRESHOLD=0.6`, 라운드마다 `+0.05`) 이상 중 최고점 미니미가 발언한다.
5. 최대 `MAX_ROUNDS=4`까지 반복하고, 발언자가 없으면 종료한다.

## E. 실행 방법

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env          # OPENAI_API_KEY를 넣으면 실제 LLM 사용
uvicorn app.main:app --reload --port 8000
```

브라우저 탭 3개로 `http://localhost:8000` 을 열고 종원 / 민수 / 지현으로 각각 입장한다.

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `OPENAI_API_KEY` | (빈 값) | 비우면 MOCK 모드 |
| `OPENAI_MODEL` | `gpt-4o-mini` | 사용 모델 |
| `TAVILY_API_KEY` | (빈 값) | 비우면 모의 검색 |
| `SPEAK_THRESHOLD` | `0.6` | 발언 임계값 |
| `MAX_ROUNDS` | `4` | 한 번의 토론 최대 라운드 |

## F. 시연 화면 (`demo-v1.html`)

서버 없이 브라우저에서 열어 재생하는 단일 HTML이다. 12단계 시나리오(가입 → 미니미 생성 → 채팅방 생성 → 입장 → 안건 입력 → 의견 교환 → 자리 비움 → 대리 참여 → 자료조사 → 결론 → 복귀 → 확인)를 보여 준다. 현재 시나리오는 기획 변경 전의 해커톤 팀(종원·민수·지현) 예시이며, 새 방향('스피치와 토론' 팀플)에 맞춰 바꿀 예정이다.
